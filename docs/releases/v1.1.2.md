# Release v1.1.2 — Frontend correction + infra fixes

**Date:** 2026-09-15
**Scope:** Math-challenges frontend correction, delivered to staging then production.

## Summary

A small frontend correction was delivered through the normal pipeline (staging via
`master` push, production via release tag `v1.1.2`). The deploy surfaced four latent
infrastructure issues in the Helm chart / ArgoCD pipeline. All were fixed and committed
to `infra/k8s/charts/portfolio`, so the fixes persist for future deploys.

The frontend release itself deployed cleanly; the issues below were pre-existing and only
became visible during this release.

## Issues & fixes

| # | Symptom | Root cause | Fix |
|---|---------|-----------|-----|
| 1 | RabbitMQ pod `CrashLoopBackOff`; `Cookie file /var/lib/rabbitmq/.erlang.cookie must be accessible by owner only` | Cookie file on the PVC had broader-than-`0600` permissions (`fsGroup: 999` + RabbitMQ auto-generated cookie left it group-readable). Erlang refuses to boot. | `fix-permissions` init container (runs as root) now `chown 999:999` + `chmod 600` the cookie before RabbitMQ boots. Repairs the existing file and prevents recurrence. |
| 2 | ArgoCD syncs stuck `OutOfSync`/`Progressing`; changes never rolled out; manual force-sync needed every time | ArgoCD sync operation waits for **all** resources to be healthy. alertmanager (see #3) was crash-looping, so the operation hung in `Running` forever; automated sync won't start a new op while one is running → every change queued behind it. | Resolved by fixing #3. Once alertmanager was healthy, the health-wait cleared and queued changes (including the frontend) rolled out automatically. |
| 3 | alertmanager `CrashLoopBackOff` for ~13 days; `Loading configuration file failed ... missing to address in email config` | `observability.alertmanager.smtp.to` empty in base `values.yaml`, rendering an invalid email receiver (`to: ''`). | Email receiver made conditional on `smtp.to` in `templates/infrastructure/alertmanager.yaml`. When `to` is empty, the receiver renders as a valid no-op. |
| 4 | Production sync `op=Failed`; `ConfigMap "grafana-dashboards" is invalid: metadata.annotations: Too long: may not be more than 262144 bytes` | The ConfigMap inlines 4 dashboard JSON files (~460 KB). Client-side apply writes the full manifest into the `last-applied-configuration` annotation, exceeding the 256 KB annotation limit. | Added `argocd.argoproj.io/sync-options: ServerSideApply=true` to `templates/configs/grafana-dashboards-configmap.yaml`. SSA doesn't use that annotation, so the limit no longer applies. |

## Topology notes (confirmed during this release)

- A **single ArgoCD instance on `forge-1`** manages both `portfolio-staging` and
  `portfolio-production`.
- **Production workloads run on a separate cluster (`portfolio-k3s`)** that the forge-1
  ArgoCD targets. To inspect production pods/ConfigMaps, use that cluster's kubeconfig
  (`/etc/rancher/k3s/k3s.yaml`), not forge-1.
- **`portfolio-production.spec.source.targetRevision` is empty** → ArgoCD tracks `master`
  HEAD, **not** the git tag, despite release tags being created. Production auto-follows
  master rather than being gated on tags.
- Both environments use `syncPolicy.automated` with `prune` + `selfHeal`, and
  `syncOptions: ["ServerSideApply=true"]` at the app level.

## Discrepancy with docs/CI-CD.md

`docs/CI-CD.md` describes production as **manual sync** gated on **semver tags**. In
reality (as of this release) production uses **automated sync** and tracks **`master`
HEAD** (empty `targetRevision`). Decide which is intended and reconcile doc vs. config.
